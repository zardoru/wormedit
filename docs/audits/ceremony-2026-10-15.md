## Findings

### CE1 V — Routing by asking every group whether it recognizes an enum

**Unwrap.** A handler's optional means both “this enum isn't mine” and “this group might produce a result.” Readers must traverse groups before discovering the owner, and `finish_compose_action` is repeated on each successful probe.

**Size/evidence.** 37 exact `if (auto result/response = f(context))` probes across two files: 20 in `application_command_dispatch.cpp` (17 at 1176–1192 in `invoke_application_command`, three at 770–772 in `compose_auxiliary_command`); 17 in `compose_actions.cpp` (seven at 2806–2817 in `dispatch_compose_remaining_action`, ten at 2906–2937 in the outer view dispatcher). These are probe counts, not action counts. Additional nested routing verified at `compose_actions.cpp:2358` (BMS choice/statement/block groups), `compose_actions.cpp:626` (view group), and `compose_resource_actions.cpp:816–834` (resource subgroups). The route is already encoded by the enum in `src/ui/frontend/actions.h:37` and command kind; group handlers inspect it again.

**Disagreement.** Some groups use a switch, some multiple comparisons. Quantize/area dispatch has intentional precedence, including `compose_area_clear_requested` with action NONE (`compose_actions.cpp:2705,2906–2910`); captured semantic targeting and fallback routing must not be reordered blindly. This is not evidence that every branch can become an unordered table.

**Owner/shape.** One enum→handler route at the boundary, one completion call. Keep exceptional pre-dispatch policy explicit. Prefer a direct switch unless a constexpr table makes ownership clearer; avoid a routing table plus another full switch/list.

```cpp
// pre-dispatch compatibility/area-clear rules remain explicit here
const auto outcome = perform_compose_action(context); // one exhaustive route
return finish_compose_action(context, outcome);
// the routed handler returns an outcome, never “not my enum”
```

**Placement:** new T-636, after T-630 and T-620 sys/UI, before T-621. **Rough size:** medium/large, two dispatchers plus exact group callers and route tests, 3–5 checkpoints. **Risk:** medium/high (precedence, unknown enums, notification count); exhaustive route inventory and parity tests required.

### CE2 V — Core event edits still write the transaction execution algorithm

**Unwrap.** Construct transaction → forward to overload → ready check → limits → borrow outcome → mutable copy → construct visitor context → visit → diagnostics/changed gate → finish/commit. The mutation itself is hidden among this algorithm and per-module effect/context types.

**Count/evidence.** Five same-shape history→transaction forwarders verified: `bpm_editor.cpp:262–265`, `marker_editor.cpp:450–453`, `pause_warp_editor.cpp:382–385`, `scroll_speed_editor.cpp:289–292`, `timing_anchor_editor.cpp:135–138`. Three further relatives: `audio_offset_editor.cpp:124–128`, `bmson_sound_channel_editor.cpp:1700–1706`, `sv_recipe.cpp:1721–1724` (the last forwards to an internal transaction function). Do not label all eight identical. Their five primary transaction bodies begin at 268,456,388,295,141 respectively; SV's framework is at `sv_recipe.cpp:1699–1724`.

**Disagreement.** BPM has optional effect + post-edit native-chart extension (`bpm_editor.cpp:281–291`); marker has text-total validation (`marker_editor.cpp:480` onward); anchor has a returned effect; pause/scroll carry `changed` and label on contexts. SV's history overload enters the internal function directly while the transaction overload checks readiness first. These are responsibilities to name, not erase. History entry points and stamped transaction entry points are both used: `timing_lane_controller.cpp:484–600,998–1019` demonstrates both. Deleting every forwarding overload would just spread transaction construction to callers.

**Owner/shape.** The transaction owns execution/finish, not the edit's domain policy. Extend that owner with a compile-time operation protocol and keep at most one convenience adapter for the unstamped boundary. No new parallel result envelope (T-633 owns effects).

```cpp
struct marker_operation_t {
    auto validate(const song_document_t&) const -> diagnostic_list_t;
    auto apply(document_command_transaction_t&) const -> edit_effect_t;
    // optional named postvalidation when this domain needs it
};
return transaction.execute(marker_operation_t{action, limits});
```

This sketch is illustrative: inventory copy timing and diagnostics before choosing signatures. It must not eagerly copy for a validation rejection, discard postvalidation, or introduce callbacks/type erasure.

**Placement:** new T-637 (with CE3), after T-633/T-634/T-632, not an expansion of the proposal runner into a different lifecycle. **Rough size:** large, five editors first, 4–6 checkpoints; evaluate the three relatives individually. **Risk:** high (copy/commit order, one finish, labels, warnings and no-op semantics).

### CE3 V — “Find one unambiguous target” is copied and means different things

**Unwrap.** Each domain spells out find, missing, count, duplicate, sometimes zero, and typed lookup after a global count, before reaching the value update. This is a query with a real policy, not a new command class.

**Verified population.** Eight query/guard owners in seven files: `bpm_editor.cpp:43` (`unique_bpm_event`), `pause_warp_editor.cpp:81` and `scroll_speed_editor.cpp:45` (`unique_event`), `timing_anchor_editor.cpp:20` (`unique_anchor`), `marker_editor.cpp:46` (`validate_chart_object_id`), `measure_editor.cpp:52` (`unique_measure`), and `semantic_layer_editor.cpp:86,179` (layer and note uniqueness). Additional same-concept BGM query at `semantic_layer_editor.cpp:356–375` is a ninth owner. Related chart uniqueness at `marker_editor.cpp:177–184` and `marker_navigation.cpp:40` is a separate ID domain.

**Copies disagree.** BPM counts only `chart.bpms`; pause/scroll use `chart_object_id_count` across collections; anchor explicitly rejects zero and counts globally up to two before typed lookup; marker rejects zero and globally counts before later kind checks. Semantic layers and measures count their own collection. These differences affect malformed inputs and rejection order. **Q:** should BPM eventually reject cross-kind collisions like scroll/pause? No permission inferred from D19, which lists specific approved behavior changes. Preserve policies now.

**Owner/shape.** One query primitive near document/chart identity queries, with explicit scope/zero/order policy and domain diagnostics supplied once per operation. Basic chart access belongs on the chart. Do not replace distinct missing-target text with a generic error without approval.

```cpp
const auto target = chart.unique_target<bpm_event_t>(id, bpm_target_policy);
if (!target) return reject_with(target.error(), bpm_target_messages);
// only BPM value validation and mutation follow
```

**Placement:** CE3 is a second part of new T-637, sharing editor ownership; query migration can precede its execution part. **Rough size:** medium, nine queries and direct callers; count future extensions separately. **Risk:** high for error ordering, low for a policy-preserving primitive. Require fixtures with zero, absent, same-kind duplicates and cross-kind collisions.

### CE4 V — Three bounded “latest request wins” jobs repeat the real lifecycle

**Unwrap.** The decoder/analyzer is surrounded by generation wrap, pruning terminal jobs, capacity checks, scheduler error mapping, submission, cancellation of old work, retaining workers, current-only publication, wait/poll and shutdown joins.

**Count/evidence.** Three owners: `src/audio/waveform_job.cpp:17–84,107–144`; `src/visual/image_job.cpp:165–238,263–299`; `src/visual/video_job.cpp:106–264,289–325`. Each has constructor/reserve, destructor cancel+wait, `discard_terminal_jobs`, begin capacity/generation/submission bookkeeping, poll completion over all workers, wait current, cancel, and is_busy: eight lifecycle blocks per owner, 24 blocks total. Public completion/start conversion shells are T-620/T-633, excluded from this count/claim. Search of `workers_`, `current_generation_`, `graph.outcome` across audio/visual/core found this exact lifecycle only in these three job files; block-cache session generation is a different owner.

**Disagreement.** Identity differs (asset vs project+revision), request validation/work differs, per-kind error strings and hard job caps differ. The verified shared publication rule is the same: erase every terminal worker, return only current generation, reset current on that completion. Cancel clears current immediately but workers stay until terminal/joined. Preserve that, and preserve cancellation of old work only after successful submission.

**Owner/shape.** A bounded job owner instantiated with typed identity/payload, reusing task_graph and `async_job_completion_value_t`, owns lifecycle once. The image batch/video-session/waveform algorithms remain named work functions.

```cpp
// type owns lifetime, generation, capacity and typed completion
return pending_.submit(identity, request, scheduler_, decode_images_task);
// owner-specific policy validates request; pending_ does not know images
```

No new stored std::function, extra allocation or virtual dispatch. Use existing scheduler task callable storage rather than adding another layer; exact compile-time submit shape to be settled in inventory.

**Lead verdict.** `src/audio/block_cache.cpp:287–295` take_ready owns a lock and active/token check; `source_registry.cpp:262–265` take_probe_failures atomically exchanges a protected queue. They are useful invariant boundaries, not empty ceremony, and must **not** be folded into the job template. Waveform poll adapter is already planned, but its worker lifecycle is new.

**Placement:** new T-635 (async shell), after T-620/T-633. **Rough size:** medium/large, three jobs plus one shared owner and tests, 3–4 checkpoints. **Risk:** high (lost wakeups, worker lifetime, latest-generation publication); no change to explicit shutdown order.

### CE6 V — Timing kind→storage/type routing is repeated after shared edit values

**Unwrap.** Timing operations repeatedly switch through the same eight lanes to find the chart vector, value alternative and edit operation. T-624 removed action payload translations, but did not remove this access knowledge.

**Count/evidence.** Six switches in one file, `src/core/timing_lane_controller.cpp:44,126,148,195,480,996`: load_existing_event, is_value_of_kind, is_same_row_is_occupied, is_target_occupied_by_unselected, apply_timing_lane_preview, delete_existing_timing_lane_event. The first four alone account for lookup/type/occupancy routing before the edit. Related projection mapping at `src/sys/compose_view.cpp:2203–2215` (clipboard variant→timing lane) is another table of the same type fact; treat it as a supporting boundary, not an excuse to merge UI labels.

**Disagreement.** Stop and delay share pause storage and value but filter pause.kind; warp uses span.begin instead of position; BPM has fixed-initial rules; some operations need selected-ID exclusion. These are named traits/policies. `is_value_of_kind` cannot distinguish stop vs delay by variant alternative alone. Unknown-kind fallbacks differ (false for load/value, true for occupied); preserve them until an owner chooses otherwise.

**Owner/shape.** A core timing event catalog/access visitor owns kind→storage, position accessor and value kind once. Operations stay distinct.

```cpp
return visit_timing_events(chart, kind, timing_occupancy_query_t{position, excluded});
// traits for warp: position = span.begin
// traits for stop/delay: storage = pauses, filter = pause.kind
```

Use a typed visitor or traits, not six new tables, dynamic dispatch or callbacks. Keep BPM semantic validation separate.

**Placement:** new T-639, after T-632/T-634, before T-621. Distinct from T-611's enum labels and selection-kind↔timing-kind mapping, and T-624's shared insert/update/delete payloads. **Rough size:** medium/large, controller + shared access helper + one projection caller, 2–3 checkpoints. **Risk:** medium/high (pause filtering, initial BPM, occupancy endpoint semantics).

### CE7 V — Action capability is a remote variant allowlist

**Unwrap.** To know whether an action can run on a virtual cursor, the reader must consult a 19-alternative probe list far from the action handler, then navigate visitor and handle forwarding layers.

**Count/evidence.** `src/core/interaction.cpp:1732–1754` lists 19 alternatives, including the conditional delete-selection exception; `1792–1800` applies its guard. There are 38 `handle` overloads at 1884–2162; `editor_action_visitor_t` at 2165–2199 adds eight explicit special overloads beside the generic forwarding overload, because some need absolute cursor/view arguments. Examples of no-information hops: `1908–1925` and `2077–2085`. Actual algorithms elsewhere remain valid owners; this does not say all 38 handles are redundant.

The terminal-action probe at `1843–1855` and active-gesture policy belong to T-634 already; they are not new findings or proposed second policy owners here.

**Disagreement.** Delete is allowed on a virtual cursor only when selection is nonempty; navigation needs absolute row; selection needs initial view. Generic “all actions may run” defaults would change behavior when a new alternative is added.

**Owner/shape.** A typed action handler/traits owner declares capability beside execution, with an exhaustive compile-time check for every variant alternative. Supply the once-built dispatch context, not a new heap bundle. The virtual-cursor policy queries the selected action once.

```cpp
struct delete_selection_operation_t {
    static auto can_use_virtual_cursor(const editor_interaction_state_t& s) -> bool;
    static auto perform(editor_dispatch_context_t&) -> editor_interaction_result_t;
};
// one visitor: check this action's capability, then execute its real operation
```

**Q:** handler traits versus methods on existing aggregate action types? Keep construction/query style and avoid a second registry. This choice needs owner review; the requirement is one location per action, no silent permissive fallback.

**Placement:** new T-640, after T-634, coordinated with T-635 (different dispatcher). **Rough size:** medium, interaction header/source and exact helpers/callers, 2–3 checkpoints. **Risk:** medium/high (dispatch order, nonempty-selection exception, eager view construction). Measure reading benefit on one action before migrating the rest.

### CE8 V/Q — The compose protocol itself adds repeated declarations

**Unwrap.** Each action repeats struct, equality, validate/perform declarations and static_assert, then reopens bodies with aliases for context.action and the application owner. This is the user's second lead, but it is a protocol review on the running T-630, not a new migration.

**Counts/evidence.** 46 explicit `static_assert(compose_action<…>)` in three paths: 24 `src/sys/compose_actions.cpp`, 15 `src/sys/compose_actions_internal.h`, seven `src/sys/compose_area_actions.cpp`. ```

**Placement:** addition to T-630, re-count after its remaining action families. **Rough size:** small review initially; broad rewriting only if owner accepts a concrete before/after sample. **Risk:** low behavior risk, medium risk of replacing useful explicit structure with clever machinery.

### CE11 V — Application commands still unpack, rebind and publish separately
