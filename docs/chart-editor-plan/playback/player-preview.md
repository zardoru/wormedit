# Plan slice: player-like preview and video export

[Back to playback and audio](../playback-audio.md).

Provide a live player-style chart preview inspired by DDReam, osu!mania, and StepMania that shows the chart moving through its active skin/layout against receptors while the music plays. This is a visual simulation, not a rules engine: its required contract has no hit windows, judgement, combo, life gauge, failure state, score, replay, or chart-validity assumptions. It uses the same timing, warp, scroll/SV, lane-layout, branch-projection, BGA-event, and sample-frame transport evaluators as editing and export. Authors can start at the cursor or selection, seek, loop a section, and watch taps, holds, stops, scroll changes, split stages, kiai, BGA changes, and other supported presentation state at their effective times.

The live player preview is modeless and does not require leaving Compose, Timing, Metadata, or another editing context. Expose it as a resizable dock, detachable panel, or bounded picture-in-picture overlay whose visibility is independent of the active workspace tab. Opening, focusing, resizing, or hiding it must not change the active edit tool, selection, cursor, snap, or shortcut context; ordinary editor input continues to edit unless a later explicit interactive-playtest capture is armed. It shares the existing transport position, seek, loop, playback rate, active difficulty/branch, audio session, and BGA state instead of starting a second player clock. Document edits publish a new immutable visual schedule at a frame boundary, so the preview updates without a mode transition and never reads a partially mutated chart. Provide at least a neutral receptor/lane presentation plus profile-aware arrow and mania-style skins; these are presentation choices over one evaluator, not separate gameplay implementations.

Build one immutable preview schedule from exact chart events and map it to audio sample frames. Playable keysounds, autoplay/BGM, BGA/background/layer/video changes, timing/metronome events, and storyboard commands each use a pre-sized contiguous event array (or typed span in one packed schedule) sorted by sample frame and stable source/draw order. A seek or loop jump binary-searches every affected family to set its small head index/handle; ordinary playback advances those heads without removing elements or allocating queue nodes, and schedule replacement builds a new bounded buffer off the realtime path. Simultaneous BGM events retain source order and polyphony, while simultaneous BGA events retain deterministic layer/draw order. An active video derives its exact reduced media timestamp from the shared sample-frame clock and its activation event, so live seek and offline rendering request the same decoder frame without retaining timing state in a frontend. Music and keysounds use one device clock, one output format, and a bounded mixer. Seeking or changing the active branch/difficulty invalidates the old schedule, kills voices from that transport session, and starts a newly identified session. Missing, undecodable, or late keysounds and visual assets produce event-linked diagnostics without blocking the rest of preview.

Keep application-side preview state in a dedicated presenter that owns revision caches and the borrowed scalar-view storage. The presenter may depend on core evaluators and resource decoders but not on Nuklear or SDL renderer types. Frontends—including a possible later wxWidgets adapter—and offline renderers consume the same bounded scene/view data while owning their own widgets and GPU textures.

## Very-late selected-area video export

The area-selection context menu offers **Export player-preview video** for the selected exact chart interval. Offline rendering drives the same player-style scene and shared audio/BGA/storyboard schedule from a deterministic sample-frame clock, with explicit resolution, frame rate, skin/layout, lead-in/out, and audio-mix options. It renders and muxes through the optional video-encoder boundary to a temporary output, reports bounded progress and cancellation, and atomically publishes only a validated completed file. An empty/stale selection, unsupported encoder, missing asset, cancellation, or render/encode failure leaves the project and any existing destination untouched. This remains deferred until live player preview, transport, visual assets, and offline video infrastructure are stable.
